# 0085: the videox include-set regression that every per-directory gate missed

Date: 2026-09-05. Round: after the Gate 1 kill of the record layer (`l2-record-gate1-result.md`).
Status: **landed and published as 0085** — tree `01e8b1eae19a33684b8769415ba16647d1de452a`, series of
85 patches, `git am` reproduction verified. A whole-tree build of the same tree is running as a
resumable background stage and is *not* claimed until it completes.

## 1. How it surfaced (the part worth recording)

While writing up the Gate 1 result I stated in `l2-recovery-and-record-probe.md` that
`videox/disp_helper.c` "has no `obj-y` line, so the wiring is owed". Checking that claim to make the
sentence precise produced the opposite: the line exists (0081 wired it), so the *reason*
`disp_helper_get_option/_get_stage/_option_init` had no provider in `undeps.py`'s output was
something else. That "something else" turned out to be a broken build.

What was actually true: 0084 replaced `drivers/misc/mediatek/video/mt6768/dispsys/display_recorder.h`
with the vendor file. The vendor header starts

```c
#include "mmprofile.h"
```

and `mmprofile.h` lives in `drivers/misc/mediatek/mmp/`. `dispsys/Makefile` (generated by
`l2slice.py`) lists `mmp/` in its `ccflags-y`; `videox/Makefile` (hand-written in 0081) listed only
`include/`, `video/mt6768/` and `video/` — and `videox/disp_helper.c` includes
`../dispsys/display_recorder.h`. Behind that, a second one: `mmprofile.h` → `ddp_info.h` → `ion.h`
(`drivers/staging/android/mtk_ion/`), also absent from the videox list.

So from 0084 on, in the published tree:

```
$ make ARCH=arm64 CROSS_COMPILE=aarch64-buildroot-linux-gnu- drivers/misc/mediatek/video/
drivers/misc/mediatek/video/mt6768/videox/disp_helper.c:19:10: fatal error: mmprofile.h: No such file or directory
make[4]: *** [scripts/Makefile.build:287: .../videox/disp_helper.o] Error 1
```

while `make .../dispsys/` — the directory every L2 gate named — returned rc=0. The series was
slice-green and tree-broken simultaneously.

## 2. The fix, and why it is one file

`videox/Makefile` regenerated with the same include set `l2slice.py` computes for `dispsys`
(stock `dispsys` + stock `videox` `-I` lists, filtered to directories that exist in this tree),
keeping `obj-y += disp_helper.o`. The header comment now says so in the file rather than in prose
elsewhere.

```
$ git -C <series> diff --name-only HEAD~1 HEAD
drivers/misc/mediatek/video/mt6768/videox/Makefile
```

No source file is touched; no vendor file is newly copied. The two directories include each other's
headers, so a per-directory subset of `-I` was never going to be right; the vendor tree does not hit
this because its `videox/Makefile` gets those paths from `MTK_PLATFORM`-wide variables the port does
not carry.

`disp_helper.c` itself stayed byte-identical to the 0081 copy (the 29 diff lines against vendor are
0081's, all of them the `CONFIG_MTK_FB` guards around the FAKE_LCM cases, which need
`videox/primary_display.c` — not ported).

The `disp_helper.c:290` warning is vendor code as it stands — the `DISP_OPT_PERFORMANCE_DEBUG` case
of the switch in `disp_helper_get_option()` has no `break`, so it falls through to
`DISP_OPT_SWITCH_DST_MODE`. It is *seen* for the first time because this is the first build that ever
compiled the file, not *caused* by this patch (0085 changes no dispsys input: the `git diff` above is
the proof). It is left alone: annotating or restructuring it would be an unrequested behaviour
edit, `CONFIG_WERROR=n`, and the kernel only adds `-Wimplicit-fallthrough=5` as a warning.

## 4. Process fixes, so the class cannot hide again

1. **The gate builds the parent, not the directory under review.** `l2-slice-gate.sh` now targets
   `drivers/misc/mediatek/video/` and derives the expected-object list from the `obj-y` of *every*
   landed Makefile in the slice (`SLICE_DIRS`). A gate that names one leaf directory certifies one
   leaf directory.
2. **Include requirements travel with shared headers, not with the `.c`.** Any patch that replaces a
   header consumed by another directory must re-derive that directory's `-I` set. Worth a rule for
   the rest of the port: 0084's header substitution was fine *for dispsys* and broke videox.
3. **`undeps.py` accepts several object directories** (`--objs d1 d2 …`), because a symbol satisfied
   by a sibling directory is not a blocker — and, symmetrically, "provider landed, not built here"
   must **never** again be read as "not wired". It now means: built by a *different* goal, or genuinely
   unwired, and you have to build the other goal to tell which. That misreading is exactly what
   almost shipped a false claim.
4. **Publishing is scripted and self-checking** (`upstream-port/bin/publish.py`, new). It refuses to
   run on a dirty tree or against the wrong tree hash, renumbers every `Subject:` with a fold-tolerant
   regex (the stored patches read `Subject: [PATCH 84` / `/84]` — a literal `[PATCH NNNN/NN]` does not
   match, and one unmatched file silently ships a 84/85 mix), asserts the file count before and after,
   and finishes by `git am`-ing the whole set in a scratch worktree to compare trees.
5. **Two documentation defects found and fixed in the same pass**, both from carrying generated text
   forward by hand: the cover letter's verification bullet cited `1bbd779e…` (the 0001-0083 prefix) as
   "all 84", and its diffstat was the 0081-era one (81 subjects, 855 files / 91713 lines). Both are
   now re-derived with `git format-patch --cover-letter 0996e0926..HEAD`; `MANIFEST.txt`'s header
   counts were stale the same way and were rewritten with the measurement that produced each number.

## 5. What this does *not* mean

* It is not a display-capability change. No panel, no DSI, no first frame, no backlight, no
  hardware at all — nothing in this round touches what runs on the phone.
* It is not a link. The 0085 gate compiles 15 objects; `vmlinux` for the whole tree is a *separate,
  still-running* stage (below) and until it says otherwise the whole-tree state after 0082-0084 is
  "0085 tip building", not "verified".
* It does not reopen the record-layer decision. Gate 1's verdict stands: option A is not
  implementable as framed, and **B vs. stopping the display port at the 0084 substrate is still the
  user's call.** What changes is that whichever way that goes, the base it sits on now builds as a
  whole tree again.

## 6. Whole-tree build, in flight

`portwork/fullbuild0085.sh` → worktree `portwork/buildfull` at the 0085 tip, `defconfig` +
`configs/apply.sh` (`.config` sha256 `758ae54339bf…`, identical to the 0084 tree's — as it must be for
a Makefile-only patch), `make prepare` rc=0, then `-j2 vmlinux` → `Image.gz-dtb` → `modules`, each
stage logged to `portwork/logs/full-0085-<stage>.log` with a one-line summary appended to
`portwork/logs/full-0085.summary`. At the time of writing stage 10 was at 849/≈7,400 objects after
~20 min on 2 CPUs (≈3 h projected); the stage is incremental, so it can be resumed in a later round
without rebuilding what landed. Results will be recorded in `build.json` as its own gate entry, and
the absence of a result is not evidence of success.
