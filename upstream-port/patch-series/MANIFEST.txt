     drivers/soc/mediatek/mtk-cmdq-helper.c, so a vendor-owned twin could not reuse them, and one
     client API in the tree is what keeps DRM_MEDIATEK users and this port from diverging.
     Encoding honesty on cmdq_pkt_wait_no_clear: it introduces NO new instruction. 4.19.325 appends a
     WFE with arg_b = CMDQ_WFE_WAIT | CMDQ_WFE_WAIT_VALUE and arg_c zero; in this tree

     cmdq_pkt_wfe() ORs in CMDQ_WFE_UPDATE only when clear=true, so cmdq_pkt_wfe(pkt, ev, false) is
     bit-identical. Both sources were read to establish this; an earlier note in this effort claiming
     mainline "cannot express wait-no-clear" was wrong and is retracted here as well as in the plan.
     Documented mechanism difference on cmdq_pkt_flush: the vendor's blocking branch
     (4.19.325 mtk-cmdq-helper.c:2073, selected because CONFIG_MTK_CMDQ_MBOX_EXT is unset on even -
     even_defconfig:1807) waits on a completion signalled by the EOC callback. Reusing that here
     would not block at all: this tree's cmdq_pkt_flush_async() calls mbox_client_txdone() itself
     right after mbox_send_message() ("We can send next packet immediately, so just call txdone"), so
     the completion is already done at submit time. The port finalizes and blocks on mbox_flush(),
     which cmdq_mbox_flush() implements by draining the thread's pending list, and that returns
     -ETIMEDOUT where stock would have hung. CMDQ_PKT_FLUSH_TIMEOUT_MS 1000 is a policy choice, not a
     measured value, and is labelled so in the header. cmdq_pkt_flush_threaded keeps stock's contract.
     cmdq_dev_get_event resolves gce-event-names, gce-events and #gce-event-cells, which this port's
     device tree does not carry, so on even it currently returns an error; no default event number is
     invented, and the display round must supply the DT properties.
